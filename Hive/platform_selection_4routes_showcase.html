📌 核心架構原則：分層選型與業務/分析分流（避免包裹採購或買錯平台）：
1. 嚴格分流兩大主線：應用整合主線（API Gateway / iPaaS 解決系統間即時交易呼叫）與 資料分析主線（CDC / Data Lakehouse 解決多廠資料彙總與 BI 對帳）解決不同問題，進入分析平台的資料不必一律繞經 API Gateway。
2. 四大路線定位：以 Azure 原生體系 為首選基準（與 D365 F&O 及 MS SQL 零阻力匹配、維運技轉門檻最低）；以 GCP 體系 為巨量數據分析對照；以 AWS 體系 為全球節點對照；以 Open Source 體系 保留海外廠區 48~72hr 斷網自律生產能力。
3. MuleSoft Anypoint 定位釐清：MuleSoft 屬大型企業級 iPaaS，本質為「複雜交易流程編排與 API 發布」，無法取代「巨量資料分析、CDC 與湖倉平台」；其數千萬元計價模式不適合作為第一階段資料底座。

🏆 路線 1：Microsoft Azure 原生體系 (官方推薦基準首選)
Baseline Candidate
🛡️ 邊界安全：Front Door ＋ Private Link
Layer 7 WAF 阻斷 OWASP 攻擊、海外廠 IP 白名單綁定、全 PaaS 私網隔離。
🚪 企業 API 閘道：Azure APIM
OpenAPI 3.0 契約治理、JWT 驗證、依海外廠區配額限流、微軟官方託管。
⚡ 微服務與佇列：Container Apps ＋ Service Bus
託管 C# .NET 8 微服務（ERP 訂單、4-Gate 產前門禁），秒級自動擴展；Service Bus 保證 FIFO 交易完整性。
📥 雙軌資料管線：Synapse Link ＋ ADF SHIR
D365 經官方 Synapse Link 零代碼入湖；各廠現場 MS SQL 經 ADF 離峰排程打包傳輸。
💡 為什麼將 Azure 列為第 1 候選？
1. D365 F&O 核心壁壘：D365 採 C++ 核心雲端 SaaS，微軟封閉底層 SQL 日誌，只有 Azure 原生 Synapse Link 具備官方唯一支援的零衝擊增量入湖能力。
2. 規避 2026-11-30 舊版停用風險：微軟已公告永久停用舊版 Export to Data Lake，採 Azure 可平滑直通 Synapse Link。
3. 團隊技能匹配與最低換廠商阻力：內部 IT 100% 熟悉微軟技術棧，台灣與東南亞微軟金級 SI 夥伴充沛，徹底消滅單點黑數（Bus Factor）。
🔴 路線 2：Google Cloud Platform (GCP) 受管體系 (巨量數據分析導向)
Analytics Oriented
🚪 閘道核心：Apigee X ＋ Cloud API Gateway
企業級契約治理，JWT 簽章驗證、Developer Portal 開發者訂閱門戶。
⚡ 運算託管：Cloud Run (.NET 8 容器)
無伺服器容器秒級自動擴展，運行 C# 微服務，無流量縮容至 0 節省費用。
📥 增量捕獲：Google Datastream (CDC)
無伺服器 CDC，原生解析 MS SQL Server 交易日誌，不鎖表捕獲工單異動。
🗄️ 湖倉核心：Cloud Storage ＋ BigQuery (Iceberg)
Medallion 3 層架構，BigQuery SQL 秒級查詢數十萬筆海外廠結算資料，支援 BigLake。
⚠️ GCP 面對 RSI 的挑戰與風險：
• D365 跨雲中繼阻力：D365 位於 Azure，無法直通 BigQuery，必須先在 Azure 存檔再經跨雲傳輸至 GCS，產生雙重儲存與出站流量費。
• 維運學習曲線：內部 IT 需重新學習 GCP IAM、BigQuery SQL 方言與 Cloud Composer (Airflow) 維運。
🟠 路線 3：Amazon Web Services (AWS) 受管體系 (全球公有雲生態導向)
Global Ecosystem
🚪 閘道核心：Amazon API Gateway
REST / HTTP API 支援，Usage Plans 金鑰配額限制，整合 IAM 與 CloudWatch。
⚡ 運算託管：AWS ECS (Fargate)
Serverless 容器運算，託管 C# .NET Core 微服務，ALB 負載平衡器分流。
📥 增量捕獲：AWS DMS (CDC)
讀取 MS SQL Server 交易日誌，持續增量複製 (Ongoing Replication) 至 S3。
🗄️ 湖倉核心：Amazon S3 ＋ Redshift Serverless
S3 作為開放 Data Lake，配合 AWS Glue Data Catalog 與 Redshift 分析。
⚠️ AWS 面對 RSI 的挑戰與風險：
• 服務拼裝過碎：API GW + Lambda + EventBridge + DMS + S3 + Glue + Redshift，組件極多，除錯跨度大。
• DMS 批次套用延遲：DMS 寫入 Redshift 必須先經過 S3 落地作為暫存，延遲較高。
• 同樣面臨跨雲中繼：D365 需自 Azure 落地再跨雲搬遷至 S3。
🟢 路線 4：Open Source 開源混合體系 (地端自主與零授權費)
Sovereignty & Zero-License
🚪 閘道核心：Apache APISIX / Kong OSS
高效能 Nginx/Lua 核心，外掛實作 Rate Limiting、JWT 認證與動態路由。
⚡ 運算託管：K3s 輕量 K8s / Windows IIS
部署於地端實體伺服器，運行 C# .NET 8 微服務，無任何雲端運算帳單。
📥 增量捕獲：Debezium ＋ Kafka Connect
開源 CDC 引擎，解析 MS SQL 日誌為事件流拋入 Apache Kafka。
🗄️ 湖倉核心：MinIO (私有 S3) ＋ Apache Iceberg
地端物件儲存池，Iceberg 提供 ACID 交易，Spark / DuckDB 進行清洗編排。
🛡️ 開源在 RSI 的真正價值：海外各廠「邊緣自律 (Edge Autonomy)」！
• 極致輕量推薦：海外各廠工控機運行 Envoy Proxy ＋ SQLite，海纜中斷時本地暫存，達成 48~72hr 斷網自律生產保障。
• 總部不建議全套自建：全套開源需要聘用 3~5 位高級 SRE / 大數據工程師維護 K8s 與 Kafka，內部 IT 極難接手，實質人事維運成本遠高於受管雲端。
⚠️ 特例定位剖析：MuleSoft Anypoint Platform 評估與定位界線
iPaaS vs Data Platform
企業在評估「系統整合」時經常提及 MuleSoft Anypoint Platform，但本報告明確建議 RSI 不要在第一階段採購 MuleSoft，原因在於其產品定位、技術解決的問題與成本結構完全不同：

比較項目 MuleSoft Anypoint Platform (iPaaS) RSI 第一階段需求 (Data Platform / Lakehouse)
本質定位 企業應用整合 (EAI / iPaaS)
專注於跨系統 API 治理、訊息轉換、企業服務匯流排 (ESB) 與業務工作流編排。		 資料湖倉與批次結算 (Data Lakehouse)
專注於 MS SQL 資料日誌擷取 (CDC)、外點 SD-WAN 離峰傳輸、對帳與 BI 分析。
解決的核心問題 解決「系統 A 與系統 B 如何即時互相呼叫」（如 Salesforce 觸發 ERP 建立訂單）。 解決「各海外廠生產工單如何集中到總部進行每日切帳對帳與主管晨會 BI」。
巨量數據與分析能力 無資料倉儲與分析能力。
資料進入 MuleSoft 後必須再轉拋至 BigQuery、Snowflake 或 ADLS，無法取代湖倉。		 具備原生湖倉與 SQL 分析。
ADLS Gen2 / BigQuery 直接儲存歷史大數據並支援 BI 直連秒級開檔。
商用授權與 TCO 門檻極高。
採 vCore / Core 計價模式，單年授權常達數十萬美金，三年 TCO 數千萬元，極度昂貴。		 按用量彈性計費。
受管雲端（ADF/Datastream + 儲存）每月僅數千至數萬元台幣，性價比極高。
技術移轉與維運 需專門精通 MuleSoft DataWeave 語法與 Mule Runtime 的稀缺工程師，換廠商極難。 微軟技術棧與 SQL 方言，內部 IT 與一般 SI 廠商皆可輕鬆承接與排障。
🛑 MuleSoft 決策結論：
MuleSoft 與「Airflow ＋ Datastream/ADF ＋ BigQuery/ADLS」解決的是完全不同的問題，兩者不能等價替代！在 RSI 各廠業務 API 與跨系統整合需求尚未成熟前，切忌一次性包裹採購 MuleSoft。第一階段只需採用輕量受管 Gateway（如 Azure APIM），把資源全力集中在打通資料湖倉最小閉環。
