📌 會議核心摘要與現況盤點

本次會議由 Howard 盤點 IT 現況，決議先完成「API 盤點」及「各廠區系統與底層資料」整理，再據以規劃 API 管理平台、資料治理與集中監控。

經盤點，信源 IT 現況歸納如下：
1. 廠區系統獨立：各廠區系統各自獨立運作，僅將資料定期拋轉至 ERP。
2. 缺乏 API 管理：現有 API 多屬內部 interface，尚無 API 管理工具及生命週期監控。
3. 流程標準待建：上版流程、備份復原順序及資料分級尚未建立統一規範。

1. 現況盤點優先

先盤點現況，再評估工具採購。工具以「不額外增加支出（開源自建）」為原則，明年預算聚焦頻寬升級。

2. 舊系統包裝穩定

舊系統以包裝方式維持穩定，原則上不大幅改動，確保產線持續順暢運轉。

3. 營運優先擇要推動

依公司營運優先順序擇要推動，首要聚焦生產、物料與 ERP/MES 拋轉核心場景。

4. 全面透明化與儀表板

軟體、硬體、網路、資安狀態全面透明化，最終以統一儀表板與戰情大屏呈現。

第一節：技術全貌與深層體檢討論事項

1. 工作方向與蜂巢計畫

Howard 曾任多家上市櫃公司 CIO／CISO，提出「蜂巢計畫」：對外系統須「可整合、可量化」，並符合 GDPR 等規範；公司運作比照上市櫃標準。系統建置之重點在於是否符合使用者需求並可被整合，而非僅完成開發。

2. API、微服務與文件標準

採 API First：開發前先定義與其他系統之介接方式。操作手冊改以 HTML／Markdown 產出，以利 AI 讀取並提供使用者問答。組織分工依 DevSecOps：開發、資安、維運（維運再分雲端與地端）。未來與供應鏈串接採 SD-WAN；海外連線可採 SASE。Microsoft 365 授權等級另案討論。

3. 雲端與 AI 應用方針

地端系統整體搬遷上雲之成本最高；上雲應拆分為微服務，並考量高可用性與廠商綁定問題。AI 應用分「AI 輔助」與「AI 內嵌」；日常性工作交由 AI，人員專注於創造性工作。團隊已使用工具產生 API 及文件，新系統已導入，舊系統大多尚未導入。

4. 現行 API 與系統介接現況

廠區 API 透過 IIS 部署於內部網路，對外服務僅少數。廠區間採電信商 SD-WAN／MPLS，目前運作穩定，少數廠區當地網路品質較差。尚無 API Gateway 或管理工具，僅有維護單紀錄，未建立 API 清單。現有多數 API 實為內部 interface（前後端分離、跨系統呼叫），非可對外之標準 API；對外 API 須具備 Token、認證等資安機制。各廠 MES、WMS 等系統獨立運作，僅將訂單結果拋轉至 ERP（ERP 為唯一彙總資料庫）。目前無客戶 EDI 對接，以客戶平台上傳為主；惟客戶持續要求即時生產資訊，未來勢必建置。D365 內含廠商自行撰寫之預存程序，團隊無法修改。

5. 資安原則

使用者原則上不開放外網，需經申請；系統不對外可阻擋大部分入侵。不可連網之設備（如 Pantone 色卡機）須隔離，需對外時改用另一台電腦。廠商遠端連入 OT 設備（如 TeamViewer）須納管，建議改經 SASE 過濾。資安以符合規範為目標，不追求滿分。

6. 監控與可觀測性

API 須可追蹤生命週期（呼叫對象、頻率、狀態），自網路底層至應用層皆須可視。各節點負載須可監看：低於 30% 暫不調整；達 50%–90% 時須提前向副總報告。電信商專線報表目前僅有總量，未依系統分類。

7. 上版流程與環境隔離

現行由承辦人自行上版，經內部簽核與測試後由課長把關；廠區由當地 IT 自行選擇時間上版。建議區分開發、測試、正式環境，由少數主管統一上版，並以系統排程取代當地人員手動上版。廠區夜間連線曾於今年 3 月資安事件後關閉，現已恢復。目前無內部 API 撰寫規範，建議訂定後轉為團隊共用之 AI Skill。

8. 資料庫、ODS 與資料頻率

各系統資料庫分離，跨系統需求由排程 Job 轉入 ODS 資料庫。SQL Server 版本自 2014 至 2017 不等；舊版不可對外，對外系統至少須為 2022 版以上。廠區與 ERP 之拋轉多為每日一次或事件觸發；總部目前要求半天一次，未來可能提高至每小時。每小時拋轉應屬可行，無須做到即時；須先估算資料量與頻寬負載再定案。不一定需建置大型 Data Lake：商業情境未改變前不必強行打破資料孤島，但各系統仍須落實資料治理。

9. 虛擬化、集中管理與開發工具

各廠區 VM 與資料庫獨立運作（總部 ERP 採 Always On，廠區僅做 Mirror）；已購置 vCenter，但由各廠自行管理，尚未集中。建議改採集中管理，納入戰情儀表板，以彌補各廠區 IT 能力落差。團隊 AI Skill 多為個人使用，部分透過 Git 共享；建議整合為團隊共用之開發框架。端點防護已採購 Cortex XDR。

10. 備份與營運持續 (BCP)

已執行備份，但尚未依重要性分級（P1–P4），亦無 SLA；總公司已分級，分點尚未分級。須定義復原順序（如 AD 優先），並列出各廠區優先復原之主機。目前無異地備援（DR）；不一定需高額投資，備份存放於不同建物即可。BCP 以恢復最小營運為目標；公司刻正推動對客戶之營運持續計畫，IT 部分尚待補足。

第二節：盤點規範、API平台與落地計畫

1. 盤點資料需求與 draw.io 強制標準

須提供各廠區系統清單、串接方式（如 MES 經 MES API 接入）、網路與軟體資料，繪圖工具統一使用 draw.io。API 應可被標準工具掃描。資料須定義更新頻率、品質與權限。系統異動文件依系統而異，軟體由台北控管。以 AI 工具為各系統產出架構文件，重點為資料關係圖及部署（實體）關係圖。

2. API 管理平台與 Data Lake 規劃

現況無 API Manager，亦無 Data Lake。方向：以開源方案建置 API 平台，先以第三方服務（如金流）試行串接。內部 API 現階段以優化為主，平台先於 Linux 測試機試裝。現有低程式碼系統無法直接移轉至容器平台。預算原則：工具盡量不額外支出；明年已規劃頻寬升級。

3. 端點防護覆蓋率

端點防護須達 100% 安裝，未安裝之設備即為漏洞。請廠商提供主機／AP／VM 之部署及存取關係資料以供檢核。

4. 資料權限與自助報表

目標：由 IT 提供整理完成之資料集，使用者以 AI／BI 工具自行產出報表，不再由 IT 逐一開發。現行權限綁定於前端程式；未來需於資料模型層設定權限（最小權限、依單位與層級）。資料分級（機密等級）為推動自助報表之前提。

5. 儀表板與異常分析

軟體、硬體、網路、資安之使用頻率與健康度須可於系統查詢，並可依週、月、季比較，作為向副總申請資源之依據。先蒐集 1 週、再蒐集 1 個月之運行資料，分析峰值與異常。

6. 開發環境標準化

以 VM 建置標準開發環境，內含所需工具，新進人員即可直接開發，避免個人電腦環境不一致。提供 2 台 VM，分別作為開發環境及測試環境。

7. 後續議題

分點之營運持續計畫（BCP）尚不完整，需再確認。應用場景於下次會議討論，先聚焦生產物料相關場景。新舊系統轉換議題（剩約 2 年時程）另行安排時間討論。

三、決議事項清冊

  • 先盤點、後採購：工具以不額外支出為原則，確有成效再行投資；明年預算以頻寬升級為主。
  • 執行 API 盤點：以既有清單為基礎整合，區分「內部 interface」與「對外標準 API」。
  • 開源 API 管理：內部 API 以優化為主；API 管理平台先以開源方案於測試環境試裝，對外串接以金流等第三方服務為試點。
  • 資料治理先行：不強制建置大型 Data Lake；依商業情境決定是否打破資料孤島，各系統仍須落實資料治理。
  • 每小時拋轉評估：廠區資料拋轉頻率以每小時為目標，先行估算資料量與頻寬。
  • 集中控管與戰情屏：虛擬化、監控及上版逐步集中控管，並建立戰情儀表板。
  • 標準開發環境：提供 2 台 VM（開發、測試）作為標準開發環境。
  • 穩定為首要：舊系統以包裝方式維持穩定；新系統依新標準開發。
  • 資安合規導向：資安以符合規範為目標，對外連線優先封閉或納管。

■ 前言與四大工作原則覆核 (Guiding Principles)

感謝 Duka Chen 主管於會後迅速整理出客觀詳實的會議紀錄。團隊於 11/09 確立之四大工作原則，為全體資訊同仁推進的最高準繩：

  1. 先盤點現況，再評估工具採購：工具以「不額外增加支出（開源自建）」為原則，確有成效再行投資；明年預算以廠區頻寬升級為主。
  2. 舊系統以包裝維持穩定：既有系統原則上不大幅改動，外層包裝標準 API，降低產線衝擊。
  3. 依營運優先順序擇要推動：首要聚焦與生產、物料、ERP/MES 拋轉相關的核心業務場景。
  4. 全面透明化與戰情儀表板：軟體、硬體、網路、資安狀態全面透明化，最終以統一儀表板呈現。

壹、 核心架構規範與標準定調

1. 繪圖與流程工具【唯一強制標準】：統一使用 draw.io
全集團所有系統架構圖（邏輯關係圖）、實體部署拓撲圖（IP/Port/協定）與資料流向圖，一律統一使用 draw.io（.drawio 格式）。
• 效益：開源免費、跨平台、無授權門檻，產出之原始檔可直接納入自建 GitLab 進行版本控管，嚴禁使用未授權之 Visio 或手繪草圖。
2. 技術平台架構定調：全數「自建在地端 (On-Premises)」
為保障信源數據絕對主權、達成海外廠區 48～72 小時斷網自律運轉，並避免公有雲長期昂貴租金：
• API 平台：採微軟原生 C# 的 Microsoft YARP（或開源 Kong），團隊全為 C# 工程師，技術同構、零學習門檻，可在各廠 VMware 獨立運作。
• Data Lake 平台：不搞複雜龐大的 Hadoop，採輕量地端「MinIO (S3相容) ＋ Apache Airflow (夜間排程) ＋ StarRocks (極速湖倉庫)」，相容 MySQL 協議，既有「聯銓 BI」完全零改動直接對接。
• D365 資料回歸：遵循微軟官方路徑，自 D365 透過 Synapse Link 產出 Parquet 暫存於微軟 Blob，地端每晚離峰單向拉回 MinIO 永久保存，99.9% 歷史資料與運算完全留在自有機房。

貳、 五大監控工具平台 (PMC 平台監控中心) 整合落地架構

解決軟硬網安透明化、節點負載 50%–90% 監控與專線系統分類流量：

參、 自研 API 與介面資料量 Payload 盤點規範（軟體組主責，IS 組協助）

為達成集團 API 治理、微服務標準化及評估微軟原生 YARP (Yet Another Reverse Proxy) API Gateway 落地容量，軟體組同仁須全面清查所有對外與內部介面：

一、 跨組協同量測流程（軟體組 ＋ IS 組聯合作業）：

  • 步驟 1（軟體組標記端點）：軟體組同仁清查原始碼，標註系統所有 API Controller 與 WebService 端點，區分「內部 Interface」與「對外開放 API」。
  • 步驟 2（IS 組量測 Payload 與頻率）：IS 網路同仁透過 IIS Log 分析器（LogParser）或抓包工具，協助軟體組量測各端點之「平均 Payload 大小 (KB)」、「單次最大 Response 大小 (KB)」及「尖峰每秒查詢數 (Peak QPS)」。
  • 步驟 3（雙向交叉校驗）：共同鎖定「日調用 > 10 萬次」或「單次 Response > 50KB」之 API。針對大封包 API，納入非同步拋轉或批次排程分流清單，避免白天產線尖峰時段佔滿專線頻寬。

二、 身分鑑別雙軌制衡標準（兼顧資安與微軟授權預算控制）：

  • 辦公室同仁（AD / AAD SSO）：台北總部與海外廠辦公室行政、業務、財務人員，維持 Microsoft AD / Azure AD (AAD) 單一登入與 Kerberos / OAuth 鑑別機制，確保企業層級資安稽核合規。
  • 現場產線人員（工號＋自設密碼）：海外各廠成衣裁剪、縫紉、品管等第一線作業同仁，維持現行「工號＋自設密碼」之輕量化 JWT Token 驗證機制。嚴禁為產線人員盲目開立 AD 帳號，以避免每年產生數百萬元非必要之微軟客戶端存取授權（CAL）費用。

前言：信源全球背景與 2027 蜂巢計畫戰略脈絡

信源全球（RSI Group）作為全球成衣與頂級運動休閒機能服飾智造領導企業，營運總部立足台灣，海外大規模生產聚落橫跨越南、柬埔寨、印尼等跨國生產基地。為因應跨國多廠敏捷智造、自動化產線排程與即時供應鏈協同之國際局勢，信源資訊架構正式由傳統多廠分散、手動維運模式，全面邁向「2027 蜂巢計畫（Project Hive）」新紀元。

壹、 11/09 跨國現況訪談體檢與基礎架構全貌

經 11/09 與集團跨部門 IT 同仁深度訪談，全盤檢視總公司與海外廠區現行運作實況。信源 IT 底層架構展現極高之微軟解決方案純度與本地自治能力，同時亦呈現邁向 2027 蜂巢計畫所需跨越之關鍵升級節點：

  • 微軟解決方案純度極高：全集團深入採用微軟體系（Windows Server、IIS、MS-SQL、C# .NET、Microsoft 365），同仁研發素質精純，具備極佳架構演進潛力。
  • 地端虛擬化自主運作穩健：各廠區虛擬化（VMware vCenter）與本機資料庫獨立運轉，具備天然之斷網容錯彈性。
  • 跨廠網路依賴電信專線：依賴第一線（DYXnet）MPLS/SD-WAN 專線，目前運作穩定，惟缺乏依系統分類之精細化流量與 QPS 監控。
  • 關鍵升級節點：API 管理中樞（Gateway）尚未成形、權限過度綁定於前端 UI、發布流程有待自動化主管審核機制健全。

貳、 核心治理技術戰略：DataModel 權限下沉與 CI/CD 主管審批

一、 資料權限下沉治理架構（前端控權轉移至 DataModel / RLS / CLS）：
現行由前端 C# 應用程式（如 WinForms/Web UI）控制資料權限之模式，存在重大資安架構瓶頸：使用者或惡意程式可輕易透過 Postman、腳本或第三方工具繞過前端驗證，直接呼叫後端 WebService 或直接查詢資料庫。
• 升級戰略：全面推動「資料存取控制下沉至資料模型層（DataModel）」。透過資料庫行級安全性（Row-Level Security, RLS）、欄位級遮蔽（Dynamic Data Masking）及後端微服務語意層權限強制檢查，確保無論連線發起於 UI、外部 API 或排程腳本，均一體適用最小權限原則。
二、 GitLab CI/CD 主管審批自動化部署機制（Automated Release Pipeline）：
針對目前工程師可直接連線發布至 prd 生產環境之現況，導入權責劃分（Separation of Duties, SoD）。於自建 GitLab 建立三階段流水線，收回工程師直接存取生產主機權限，全面由系統自動化驗證部署：
• build / unit-test：代碼提交自動建置與單元測試。
• deploy-test：自動發布至測試環境供業務驗收。
• deploy-prd：必須由課長/主管於 GitLab 介面按下「Manual Approval」簽核按鈕，系統方可自動執行生產環境零停機金絲雀部署（Canary Release）或藍綠切換。

參、 軟體研發同仁盤點任務與填報規格指南

請軟體研發團隊協同海外各廠資訊同仁，全面盤點總公司與海外廠區所有自研系統、部署拓撲與 API 清冊，具體執行以下四大盤點工作：

  1. 全面繪製各廠系統架構圖與實體部署拓撲圖（統一強制使用 draw.io）。
  2. 編制自研 API 清冊（Swagger / OpenAPI 3.0 標準格式，標註 QPS、Payload、驗證方式）。
  3. 梳理資料庫預存程序（Stored Procedures）與排程 Job，清查跨系統資料依賴。
  4. 檢核前端權限邏輯，標註過渡至 DataModel 行級安全（RLS）之改造成本與路徑。

肆、 基礎設施與資安（IS）同仁盤點任務與專案時程

請 IS 同仁主導全集團資料資產業務連續性計畫（BCP）清查與核心系統 SLA 等級評定，並全力支援軟體團隊量測跨國 API 資料傳輸量：

  • BCP 與 SLA 盤點清查：清查全集團所有資料庫之備份排程、還原演練紀錄，精確填報 Tier 1 (99.9%)、Tier 2 (99.5%)、Tier 3 (99.0%) 之 RTO 與 RPO 指標。
  • 跨國專線流量與 Payload 量測：分析跨國第一線專線 NetFlow 數據，協助軟體組完成前十大高頻、大封包 API 之傳輸量分析。
  • 端點防護 100% 覆蓋：清查 Cortex XDR 安裝覆蓋率，針對工業色卡機等 OT 設備落實網段實體隔離與 SASE 代理連線。
